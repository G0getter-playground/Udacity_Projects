was confirmed in. See [sdk-upgrade-resolution.md](sdk-upgrade-resolution.md) for exactly what
changed and the real, complete live run that proves it. The investigation below is kept as-is

## Reproduction

```bash
npm run dev -- octocat Hello-World 1
```

with a real, working `ANTHROPIC_API_KEY`/`ANTHROPIC_BASE_URL` (Vocareum proxy) and `GITHUB_TOKEN`
configured. Also reproduced calling `query()` from `@anthropic-ai/claude-agent-sdk` directly, in a
standalone script, bypassing this project's own orchestrator/retry code entirely — so the bug is
in the SDK, not in `orchestrator.ts`.

## What happens

Turns 1–6 are completely normal: session init, the model's plan, two GitHub MCP tool calls
(`get_pull_request`, `get_pull_request_files`), and their two tool results. Both tool results are
large — GitHub's raw PR/file-metadata JSON is verbose (the `get_pull_request` response alone is
several KB of nested user/repo objects).

Turn 7 — a **synthetic** assistant message appears, generated by the SDK itself
(`"model": "<synthetic>"`), containing:

```json
{
  "type": "assistant",
  "message": {
    "model": "<synthetic>",
    "role": "assistant",
    "content": [
      {
        "type": "text",
        "text": "API Error: 400 {\"type\":\"error\",\"error\":{\"type\":\"invalid_request_error\",\"message\":\"messages.1.content.4: `tool_use` ids must be unique\"},\"request_id\":\"req_011CeUoYa643dVVBqXTaEC2s\"}"
      }
    ]
  },
  "error": "unknown"
}
```

Turn 8 is the final result message: `"subtype": "success"` but `"is_error": true` (a contradictory
status the SDK reports as-is), and — despite this project never configuring a second model
anywhere — `modelUsage` shows a hidden call to `claude-haiku-4-5-20251001` billed alongside the
configured `claude-sonnet-4-5-20250929`:

```json
"modelUsage": {
  "claude-haiku-4-5-20251001": {
    "inputTokens": 3, "outputTokens": 218, "cacheCreationInputTokens": 11224,
    "costUSD": 0.015123

  "claude-sonnet-4-5-20250929": {
    "inputTokens": 16, "outputTokens": 798, "cacheCreationInputTokens": 35167,
    "costUSD": 0.14821155
  }
}
```

Immediately after, the Node process itself crashes:

## Root cause: the SDK's own "microcompact" feature

`node_modules/@anthropic-ai/claude-agent-sdk/cli.js` contains a context-management feature
(internal telemetry event name `tengu_microcompact`) that automatically fires once accumulated
tool-result tokens cross an internal threshold, to compact old tool output out of context. That
is what invokes `claude-haiku-4-5-20251001` — nothing in this project's code requests a second
model. The hidden follow-up call it constructs contains a duplicate `tool_use` id, which the
Anthropic API correctly rejects with the 400 above.

Two further bugs compound the crash:

1. **Inconsistent error classification.** The SDK's `SDKAssistantMessageError` type is
   `'authentication_failed' | 'billing_error' | 'rate_limit' | 'invalid_request' | 'server_error' | 'unknown'`
   — a real, deliberate classification the SDK stamps on every failed assistant turn. The
   *identical* underlying 400 was observed classified as `"unknown"` in isolated reproductions and
   as `"authentication_failed"` in full orchestrator runs — which is what made this look like an
   auth problem before turn-by-turn logging and direct reproduction traced it to its real cause.
2. **No recovery.** Rather than retrying or surfacing a catchable error, the CLI subprocess exits,
   which the SDK surfaces as a hard `Error`, not a normal failed-`result` message — so even
   generous retry logic at the orchestrator level (tested up to 4 attempts) cannot help, since
   every fresh attempt reproduces the same crash at the same point.

## Why this isn't fixable from this project's code

- No documented `Options` field disables microcompact or raises its threshold.
- It triggers on *any* conversation with two-or-more sizeable tool results — which any real PR
  review will always have, since fetching the PR and its file list are the mandatory first steps.
- It reproduced identically with `settingSources: []` (full isolation from local Claude Code user
  settings/plugins), ruling out environment contamination as the cause.
- The installed SDK (`0.1.77`) is the newest version on the Zod v3 line this project's schemas
  depend on — `0.2.0`+ requires Zod v4, a migration across every file in `src/types/` that was
  deliberately not attempted (see the README section this file is referenced from).
